# Forecasting and optimization architecture review

## Current flow

`price forecast + load forecast + solar forecast -> ForecastBundle -> rolling horizon -> MultiAssetOptimizer`

The `ForecastBundle` is the boundary between forecasting and optimization. The rolling-horizon layer consumes aligned windows and does not generate forecasts itself.

## Findings

### 1. Forecasting boundary: good
`ForecastBundle` provides separate price, load, solar and timestamp series and validates minimum horizon lengths. This is the correct seam for replacing heuristic forecasting with ML later.

### 2. Rolling horizon: good, but currently open-loop
The rolling layer solves successive windows and commits only the first dispatch interval. It currently receives one `ForecastBundle` and slices it. A production controller should regenerate or refresh the bundle before each committed interval when new telemetry/market/weather data is available.

### 3. Price fallback: safe
ENTSO-E is the production source. Synthetic prices are available only through explicit fallback, preventing silent synthetic dispatch in production.

### 4. Load forecast: deterministic baseline
The load model uses historical weekday/hour medians and a global median fallback. This is a good baseline, but not yet a probabilistic forecast and does not expose uncertainty.

### 5. Solar forecast: external weather dependency
Solar production is derived from Open-Meteo weather inputs with a simple physical model. It should remain separate from the optimizer. The next improvement should be calibration against actual site telemetry before introducing a learned model.

### 6. Time handling: important production gap
`ForecastBundle.timestamps` are strings and validation checks length, not timezone, monotonicity, or hourly spacing. Before production use, timestamps should be normalized to timezone-aware UTC instants and validated for monotonic hourly cadence.

### 7. Legacy optimizer duplication
The repository contains older optimizer modules alongside `MultiAssetOptimizer`. The new multi-asset path should become the canonical optimization entry point, but legacy modules should not be deleted until callers and tests are inventoried.

### 8. Persistence gap
The rolling result is an in-memory `RollingHorizonResult`. A production VPP needs a durable dispatch record containing VPP/site/asset IDs, forecast version, timestamps, optimization run ID, solver status, objective/cost, and committed action.

### 9. Provider failure policy
Forecast providers should expose explicit freshness/source metadata and fail closed for production dispatch when required inputs are stale or missing. Synthetic fallback should remain opt-in.

### 10. ML boundary
ML should replace or augment individual forecast providers, not enter the MILP. The optimizer should consume the same `ForecastBundle` contract regardless of whether the forecast was generated by a median baseline, statistical model, gradient boosting model, or neural model.

## Recommended next phase

1. Normalize and validate forecast timestamps/timezones.
2. Add forecast freshness and source metadata.
3. Persist optimization runs and committed dispatch.
4. Add provider health/staleness policies.
5. Benchmark rolling-horizon solve time and establish operational limits.
6. Add forecast uncertainty intervals and confidence-aware optimization inputs.
7. Only then introduce ML forecasting, starting with load and solar calibration against historical telemetry.

## Decision

Do not expand the MILP yet. Stabilize the forecast-to-dispatch production contract first. This reduces coupling and gives ML a clean insertion point later.
